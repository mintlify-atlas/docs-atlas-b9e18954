The strategy is one file per month — `main.strategy.ts` — reading top to bottom as a complete specification of everything the fund does for that month: which coins it holds, how much it allocates to each, and when it exits. There is no shared logic between months. Understanding the four mechanics in order is enough to read any month's file without further reference.

## The Four Mechanics

<Steps>
  ### Monthly Basket Selection

  At the start of every month a basket of **twenty symbols** is frozen into that month's `main.strategy.ts` as a plain constant between the `// BASKET:BEGIN` and `// BASKET:END` markers. The basket is the top-20 Binance USDT spot pairs by **quote volume of the previous calendar month**, filtered by three rules:

  - Listed on Binance at least **90 days** before the month starts (liquidity requirement)
  - Not a stablecoin, fiat pair, leveraged token, or wrapped/staked derivative of BTC or ETH
  - Tradable on the Yahoo Finance candle source for the full duration of the month

  Because the ranking uses only information that was publicly available on the first day of the month, there is no look-ahead. Delisted tokens appear in the baskets of the months when they were liquid and are absent from later ones — the opposite of survivorship bias.

  ```typescript
  // BASKET:BEGIN
  // September 2020: top-20 USDT spot pairs on Binance by August 2020 volume
  // (known before the month started), listed ≥90 days, no stables/leveraged/wrapped.
  // Generated by scripts/common/generate_months.mjs from scripts/common/universe.json.
  const BASKET = [
    "BTCUSDT",
    "ETHUSDT",
    "LINKUSDT",
    "XRPUSDT",
    "BNBUSDT",
    "EOSUSDT",
    "LTCUSDT",
    "TRXUSDT",
    "BCHUSDT",
    "BANDUSDT",
    "OMGUSDT",
    "XTZUSDT",
    "ADAUSDT",
    "ATOMUSDT",
    "VETUSDT",
    "ZECUSDT",
    "WAVESUSDT",
    "QTUMUSDT",
    "NEOUSDT",
    "ALGOUSDT",
  ];
  // BASKET:END
  ```

  The only thing that differs between the `main.strategy.ts` files of any two months is this block, the Yahoo ticker overrides in the exchange module, and the month's frame.

  ### BTC Trend Gate

  The gate is a number between 0 and 1 that answers the question: "how bullish is Bitcoin right now?" It drives how much of the deposit goes into the basket versus into gold.

  The gate is computed as the **share of six lookback windows — 20, 25, 30, 35, 40, and 45 days — on which Bitcoin's most recent close is higher than it was N days ago**:

  ```
  gate = count({ N ∈ {20,25,30,35,40,45} | close(yesterday) > close(yesterday − N days) }) / 6
  ```

  Possible values are 0, ⅙, ⅔, ½, ⅔, ⅚, and 1. Using an ensemble instead of a single moving average removes a knife-edge parameter: single lookbacks outside the 25–45 day range perform noticeably worse, but within that plateau the result is insensitive to which N is chosen. The ensemble averages over the plateau rather than picking a point on it.

  The gate is cached once per day with `Cache.fn` and a `1d` interval. Because `getCandles` is trimmed to the engine's current backtest time, there is no look-ahead even during simulation.

  ```typescript
  const GATE_SYMBOL = "BTCUSDT";
  const GATE_WINDOWS_DAYS = [20, 25, 30, 35, 40, 45];

  const getGate = Cache.fn(async (): Promise<number> => {
    const candles = await getCandles(GATE_SYMBOL, "1d", Math.max(...GATE_WINDOWS_DAYS) + 1);
    const closes = candles.map(({ close }) => close);
    const last = closes[closes.length - 1];
    const up = GATE_WINDOWS_DAYS.filter(
      (days) => last > closes[closes.length - 1 - days]
    ).length;
    return up / GATE_WINDOWS_DAYS.length;
  }, { interval: "1d" });
  ```

  ### Deposit Allocation

  Each time `getSignal` fires for a symbol, the gate value determines the cost of that position:

  - **Basket symbol:** `cost = (DEPOSIT_USD / basketSize) × gate`
  - **PAXGUSDT (gold):** `cost = DEPOSIT_USD × (1 − gate)`

  When the gate is 1 the full deposit is spread equally across all twenty basket symbols and PAXG receives no signal. When the gate is 0 the basket receives no signals and the entire deposit is parked in gold for the week.

  ```typescript
  const cost = symbol === PARKING_SYMBOL
    ? DEPOSIT_USD * (1 - gate)
    : PER_SYMBOL_USD * gate;

  // cost: 0 is silently replaced by the engine with CC_POSITION_ENTRY_COST
  if (cost < 1) {
    return null;
  }

  return {
    id: `${symbol.toLowerCase()}-${when.toISOString().slice(0, 10)}`,
    symbol,
    ...Position.bracket({
      position: "long",
      currentPrice,
      percentStopLoss: STOP_LOSS_PERCENT,
      percentTakeProfit: TAKE_PROFIT_PERCENT,
    }),
    cost: Math.round(cost * 100) / 100,
    minuteEstimatedTime: HOLD_MINUTES,
    payload: { gate, weight: cost / DEPOSIT_USD, basketSize: BASKET.length },
    note: `${symbol} gate=${gate.toFixed(2)} cost=$${cost.toFixed(2)}`,
  };
  ```

  <Info>
    **Why `cost < 1` returns `null` instead of `{ cost: 0 }`:** the backtest-kit engine silently replaces a signal with `cost: 0` with its default entry cost (`CC_POSITION_ENTRY_COST`, typically $100). Returning `null` suppresses the signal entirely, which is the correct behaviour when a symbol's gate-adjusted allocation rounds to zero.
  </Info>

  Every signal's `payload` carries `gate`, `weight` (fraction of `DEPOSIT_USD`), and `basketSize`, so the allocation decision is fully visible in the `opened` rows of `content/<month>/dump/report/backtest.jsonl`.

  ### Weekly Position Cycle

  Each position is opened with `Position.bracket` as a **long** with technical stop-loss and take-profit levels:

  ```typescript
  const HOLD_MINUTES    = 7 * 24 * 60 - 1; // one week minus one minute
  const STOP_LOSS_PERCENT    = 50;           // −50%: unreachable on spot in a week
  const TAKE_PROFIT_PERCENT  = 500;          // +500%: unreachable on spot in a week
  ```

  The stop and take-profit exist only to satisfy the engine's position validator. In practice a spot position cannot move ±50–500% in seven days, so **the only normal exit is `time_expired`**. The `minuteEstimatedTime` of `7 * 24 * 60 - 1` closes each position at 23:59, and the symbol re-enters at the next hourly tick (00:00) with a fresh cost calculated from that day's gate value.

  <Tip>
    The one-minute offset is intentional: closing at 23:59 and reopening on the 00:00 tick means the previous position is fully settled before the new weekly entry is evaluated, keeping the cache clean without introducing an extra hour of idle time.
  </Tip>

  Because basket legs and the gold leg re-enter independently, their weekly cycles drift apart after the first week in which the gate changes. This is a known, documented approximation — see `docs/HOWTO.md` for the two approaches to removing it. The repo deliberately ships the simple version.
</Steps>

## Summary

The table below maps each design aspect to the concrete choice made in this repo:

| Aspect | This repo |
|---|---|
| **Subject** | A weekly long-only crypto index fund with a Bitcoin trend gate and a gold counter-position, replayed month by month |
| **Universe** | Top-20 Binance USDT pairs by previous-month volume, 90-day listing age, no stables/leveraged/wrapped; frozen per month, no survivorship |
| **Gate** | Share of six lookbacks (20–45 days) on which BTC closed higher; scales basket exposure from 0 to 1 |
| **Counter-position** | `PAXGUSDT` receives `1 − gate` of the deposit for the same week |
| **Cycle** | Equal-weight weekly positions, time exit after one week minus a minute, re-entry on the next tick |
| **Data** | Yahoo Finance daily bars, sampled to minutes by `getCandlesSampled`, one engine step per day, tickers resolved and price-verified against Binance before generation |
| **Layout** | 73 self-contained month folders generated from one reference month; generator, universe builder, resolver and verifier in `scripts/common/` |
| **Honesty budget** | Per-symbol accounting with a fixed deposit, synthetic intraday path, legs that drift out of sync; all documented in `docs/HOWTO.md` |

<Warning>
  The data layer uses **daily bars from Yahoo Finance sampled into synthetic minute candles**. Every minute of a day carries that day's high, low, and close. For a weekly time exit this does not affect results, but intraday stop-losses would be unreliable on this data. The strategy's technical stop of −50% is chosen precisely because it is unreachable within a week on a daily-bar simulation.
</Warning>
